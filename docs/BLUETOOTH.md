# USB／蓝牙连接

**简体中文** · [English](BLUETOOTH.en.md)

本页适用于 **0.13.0 USB／蓝牙双模控制**。下列详细蓝牙实测结果为 **0.12.0 既有基线**：PIN 配对、保留绑定的应用更新后重连、Fast／Plan 桌面切换、旋钮导航高亮与原生蓝色灯效、加密元数据压力测试，以及 USB／BLE 自动切换和 Tab5 蓝牙开关重连。麦克风版本本轮只确认枚举与绑定保留，没有重跑全部 BLE 桌面联动。具体 DOM 焦点、控件身份、其他灯色与下方列出的其他场景仍未确认。历史 0.11.1 固件只支持 USB。预编译下载见 [0.13.0 Release](https://github.com/atovk/tab5-codex-micro/releases/tag/v0.13.0)，源码构建见 [README](../README.md#从源码构建)。

板载麦克风音频不通过蓝牙传输。0.13.0 增加了标准 USB 麦克风；Tab5 的 ESP32-C6 不支持传统蓝牙耳麦的 Classic/HFP 协议，自定义 BLE 音频还需要额外主机音频桥接，因此暂缓。使用方式及原因见 [麦克风说明](MICROPHONE.md)。

## 两条数据通道

| 内容 | USB | 蓝牙 |
| --- | --- | --- |
| 原生按键、旋钮、摇杆和主机灯光 | Micro USB HID | Micro BLE HID |
| 明确绑定的标题、配置及指定聊天的真实设置 | 本地 companion → USB CDC | 同一 companion → 独立加密 GATT 服务 |
| 刷机、帧缓冲截图及一般诊断命令 | USB 工具 | 未提供无线刷机或截图通道 |

原生操作仍由 Codex 桌面应用的 Micro 映射解释。蓝牙不是把旋钮、摇杆转换为通用键盘快捷键；标题和 Fast／Plan／权限状态也不是原生灯光消息自带的数据。原生 HID 连上与 companion 同步成功需要分别确认。

## 首次配对

1. 为 Tab5 供电，打开 **齿轮 → 连接 / Connections**，开启 Bluetooth。板载 C6 使用本次实测 Tab5 已有的兼容固件，无需单独刷写 C6 或其他开发板。初始化完成后可以开始配对；若页面显示初始化错误，保留 USB 检查，不要刷写其他型号芯片的镜像。
2. 点击 **开始配对 / Start pairing**。新电脑只可在这个**两分钟窗口**内建立绑定；普通启动不会自动向陌生电脑开放配对。
3. **先解锁电脑**，打开系统蓝牙设置，选择设备页面显示的名称，例如 `Tab5 Micro XXXX`。后缀用于辨认，不能替代完整芯片身份。
4. 看到电脑的配对提示后，**立即输入 Tab5 屏幕上的六位 PIN**，包括开头的零。验证码在配对握手过程中出现；尚未出现时页面显示占位符。没有统一默认 PIN，不应在未看到验证码时猜测输入。SMP 配对事务本身约 **30 秒**超时；上面的两分钟是允许新电脑发起配对的窗口，并不代表每次 PIN 输入有两分钟。超时或失败后关闭旧提示，再重新点击开始配对。
5. 完成系统配对后，打开 Codex **设置 → Codex Micro**，检查设备并配置按键、旋钮及语音映射。若系统已配对但桌面没有识别设备，这仍是原生 HID 连接问题，标题 companion 不能替代该连接。

macOS 的 PIN 提示可能是由 **BluetoothUIServer** 显示的独立系统对话框，未必嵌在「系统设置」窗口中。如果 Tab5 已显示验证码而设置页没有输入框，请立即检查被其他窗口遮住或位于其他桌面的系统弹窗；保持电脑解锁，不要只在设置页等待。若旧提示已超时，应关闭它并重新开始，使用本次新显示的 PIN。

先从 macOS 系统蓝牙设置发起首次配对并完成系统提示，再让无线 companion 继续。首次运行也可能要求 Bluetooth 权限。桥接不调用配对或取消配对 API；访问需要认证的 GATT 特征时由系统处理认证提示，设备仍要求绑定及 PIN 认证。Identity 读取最多等待 **60 秒**，这是主机读取的等待上限，**不会延长 SMP 约 30 秒的配对超时**。锁屏、未输入 PIN 或提示被隐藏时仍可能失败，而不是视为已配对。C6 可用、能搜索到设备或 MTU 协商完成均不能代替认证成功。

早期实机验证遇到了 Secure Connections 的 DHKey 检查失败（`SMP reason 11`）。[上游问题 #241](https://github.com/espressif/esp-hosted-mcu/issues/241) 记录了同类 ESP32-P4／C6 组合的 ECC 计算缺陷，并指出 ESP-IDF 修复 `9fd7cb7e606`。本项目针对固定 SDK 增加了窄范围兼容修复：只将 `uECC_shared_secret` 的共享密钥计算交给 SDK 的 mbedTLS ECDH 接口，保留 TinyCrypt 密钥生成及 Secure Connections 协议。构建脚本校验固定 SDK 身份和 `libbt.a` 的 SHA-256，身份或库内容改变时停止构建，要求重新审查兼容修复。

当前 ESP32-P4 实机已通过 RFC 5903 P-256 已知答案自测，真实六位 PIN 配对成功，并确认绑定保存到 NVS、连接已加密且通过认证。这验证了配对和加密基础，不等同于全部原生操作和断连恢复场景已经通过。

## USB 优先与重连

USB 数据接口挂载后优先承载原生输入。拔线后，已就绪的蓝牙可接管；接回 USB 后恢复有线。切换时先处理旧连接上已经提交的按键释放和摇杆归中，不把旧动作迁移或重放到另一个连接。若旧蓝牙连接无法完成释放，固件可断开该蓝牙会话来结束持有状态。

普通重启、短暂离线以及 Bluetooth 关闭后再开启会保留绑定，设备与 companion 会尝试重新连接。原生连接恢复和标题／状态恢复是独立步骤；元数据过期时显示未知，重连后从当前缓存重新读取，不重放旧快照。

当前实机已多次验证：仅更新应用分区（app-only）后重启，无需再次输入 PIN 即恢复绑定、加密和认证状态，并重新收到 BLE 元数据应答。同一个生产 auto companion 已完成 USB→BLE→USB；Tab5 蓝牙关闭三秒再开启后，原生 HID 约 1.5 秒恢复，新会话的 GATT 也自动恢复，两类元数据持续 90 秒收到严格序号应答。整个流程无需新 PIN，原生输入计数未增加，未重放旧输入。这里测试的是 USB 数据接口暂时断开和 Tab5 蓝牙开关，不能外推为物理断电、电脑蓝牙开关或长期休眠均已通过。

如果电脑或 Tab5 的绑定记录已失效，在 Tab5 点击 **清除绑定 / Forget pairing**，阅读确认框并确认，再在电脑删除旧记录并重新配对。该操作会断开蓝牙；取消确认则保留绑定。完整 factory 刷机可能清空 NVS 中的绑定与偏好，之后需要重新配对。

蓝牙只替代数据连接，Tab5 仍需电池或合适电源。固件为板载 C6 供电，保持电池充电和外部供电输出关闭；尚未提供续航或新增功耗的实机验证结果。其他 C6／ESP-Hosted 固件组合尚未验证。

## 标题与状态 companion

先按 [README 的桥接说明](../README.md#可选聊天标题和状态桥接) 准备 `.venv`，安装完整 `requirements.txt`（包括固定版本 `bleak==3.0.1`）。下载包的 `requirements-flash.txt` 只用于刷机，不包含无线 companion。

USB 连接时可用以下只读命令确认 P4 应用身份：

```sh
.venv/bin/python tools/verify_device.py discover
```

以下 `TAB5-0123456789AB` 是示例，必须替换为实际 P4 应用序列号：

```sh
# 前台单实例；USB 优先，没有匹配 USB 时使用已配对的 BLE。
.venv/bin/python tools/title_sync.py --watch --transport auto \
  --device-serial TAB5-0123456789AB
```

登录服务可替代上述前台进程：

```sh
.venv/bin/python tools/title_sync_service.py install --transport auto \
  --device-serial TAB5-0123456789AB
.venv/bin/python tools/title_sync_service.py status
```

安装时提供的串号会保存在该服务的配置中，允许无 USB 冷启动。也可设置 `TAB5_SERIAL_NUMBER`；显式 `--device-serial` 优先。候选必须唯一，随后检查 Identity 的协议字段和 P4 串号；指定串号时必须精确匹配。多个无法区分的候选不会通过名称或信号强度猜选。这是设备选择与公开标识匹配，不是密码学设备认证。

正式安装的登录后台服务也已独立实测：USB 数据接口暂离 30 秒、系统仅有 BLE 时自动恢复元数据通知，设备收到 20 条元数据命令，通知失败为零且 BLE 会话保持；USB 回归后标题、配置与聊天状态均为新鲜。

BLE Identity 返回的串号必须对应 **USB 使用的 P4 芯片串号**，不是 C6 无线 MAC。广播中的厂商数据只能缩小候选范围，连接后仍检查 Identity 响应。本项目真实固件强制该读取使用加密且经过 MITM 认证的链路；公开串号本身不能证明应答外设的真实性。USB 被截图、诊断或刷机工具锁定时，auto 跳过心跳，不会通过 BLE 绕过锁。显式 `--port` 将同步限定到该 USB 端口，端口消失后不会无线回退。

`title_sync.py` 是唯一访问硬件的 companion；其持久 BLE 连接由跨进程锁保护。不要同时运行前台 watch 与登录服务，第二个进程不会抢连或断开第一个进程的会话。另一个 `chat_state_bridge.py --thread-id CHAT_UUID` 只订阅指定聊天并更新缓存，可同时运行；标题服务不会代为启动它。

原生 USB 输入优先和 companion 的传输选择相互独立：`--transport ble` 只强制**元数据**走 BLE，不会强制原生按键改走蓝牙。`--transport usb` 完全不建立蓝牙元数据连接。

### 设备身份边界

本项目真实固件对 Identity、RX、TX 强制链路加密与 MITM 认证，首次绑定使用显式系统 PIN 配对。companion 读取后的 P4 串号匹配没有提供应用层密码学设备证明；服务 UUID、广播信息与串号均为公开标识。主动仿冒外设可以复制这些标识并以明文回应相同 GATT 接口，从而骗取元数据。主机端当前未处理这一威胁，不能据串号匹配或本固件的加密要求宣称已排除克隆设备。

## 检查与故障处理

本节蓝牙实测数据采自 0.12.0，作为既有基线保留，不代表在 0.13.0 上重跑了完整 BLE 验收。

在没有另一个 BLE companion 持有连接时，可发送一次元数据并等待应答：

```sh
.venv/bin/python tools/title_sync.py --once --transport ble \
  --device-serial TAB5-0123456789AB
```

只有 `TITLES` 与 `HOST_CONFIG` 都收到正确序号的应答后，才输出 `delivery.status: acknowledged` 和实际 `delivery.transport`。这证明设备收到了元数据，不证明原生按键已经被桌面执行。默认输出不打印标题；无需为这项检查加入 `--show-titles`。

当前实机已通过 BLE 完成这两种命令的正确序号应答验证，并通过 20 轮新七标题、20 轮相同内容的压力测试，共 80／80 正确 ACK，解析、状态、丢弃及 ACK 错误均为零，原元数据、偏好与捕获状态均恢复。该项确认元数据收发；原生桌面执行须使用独立证据，不能由 ACK 推断。

| 现象 | 检查方向 |
| --- | --- |
| 系统搜索不到 Tab5 | 确认 C6 可用、Bluetooth 开启、设备有电；新电脑需要重新打开两分钟配对窗口 |
| Tab5 有 PIN，电脑设置页没有输入框 | 检查独立的 BluetoothUIServer 系统弹窗及其他桌面；及时输入六位 PIN，超时后重新开始 |
| 输入 PIN 后报告 `SMP reason 11` | 确认使用包含 ECC 兼容修复且通过固定 SDK／库校验的构建；当前修复已通过实机自测和真实配对，延长读取超时不能替代该修复 |
| 配对后标题或状态仍未知 | 原生 HID 不包含这些文本；确认 title companion 和所需的状态桥接都在运行，绑定为本地 Custom assignments |
| 提示 metadata busy | 检查是否同时运行 watch 与登录服务，或 USB 工具仍持有共享锁；不应启动更多实例重试 |
| 指定串号后找不到设备 | 对照 P4 应用串号，不使用 C6 MAC、BLE 名称或另一块 ESP32-S3 的串号 |
| 已配对但重连失败 | 先恢复供电／电脑 Bluetooth；仍失败时在两端清除旧绑定，再在配对窗口内输入新 PIN |
| 原生按钮指向另一个聊天 | 跟踪状态不表示桌面活动目标；“操作目标未核对”仍有效，不会把 Micro 命令重定向到跟踪聊天 |

NimBLE 回调顺序问题已修复：`ENC_CHANGE` 加密状态事件或 CCCD 通知订阅早于 `CONNECT` 回调到达时，后续连接初始化会保留同一会话已经确认的状态。修复后的多次应用更新重启已通过上述无需 PIN 的重连和元数据验证。

另一个已修复问题是 Arduino NimBLE 按 UUID 去重，误删了同一 HID 服务中不同类型的 Report 特征。项目内的 `BLEService` 补丁保留全部五个 Report 特征及只读的 `0x2908` Report Reference 描述符，并使用标准 Service Changed 通知，让保留绑定的主机重新发现更新后的 GATT 服务。

macOS 已实际订阅 HID 通知，设备达到 `ready`；Codex 桌面应用收到 BLE 的 `device.status` 与 `rgbcfg` 应答，设备观察到原生会话。在进一步的受控测试中，USB 数据接口从系统消失，仅列出 Bluetooth 时，指定聊天真实状态分别完成 **Fast → Standard → Fast** 和 **Default → Plan → Default**，两项均确认了 BLE 传输与桌面执行。测试没有通过设置 IPC 写入这些变化。

旋钮四帧测试同样在纯 BLE、同一认证会话中进行，预览与冻结模式均关闭。基线、顺转后、逆转后、恢复帧显示：原生 ambient 从关闭变为蓝色 `#304FFE` 的 snake 效果，两次旋转分别触发，再自动恢复关闭；帧缓冲可见颜色符合回传颜色的 RGB565 量化。桌面只有找到可见且启用的输入区控件并进入导航选中分支，才生成这一原生反馈，输入提交提示本身不会生成它。这确认导航高亮已执行及真实灯效已回传、显示，但不证明具体 DOM `activeElement`、控件名称或两次选中不同控件；只有一个候选时可以重复高亮同一控件。同期 Agent 槽位状态保持不变，运行槽位外沿像素与霓虹帧计数持续变化，也确认了追光动画。

自动切换测试在 USB 回归后确认：BLE 保持认证、绑定和就绪，标题／配置／聊天状态新鲜，发送队列清空、无持有按键或摇杆偏移，无失败、丢弃及过期消息。它覆盖了本次有限切换流程，未覆盖持键跨断电等极端条件。

0.12.0 固件实机验收时通过 **337 项主机测试**、构建和同一 Tab5 的 app-only 刷入校验，绑定、偏好与字库保留。发布准备加入打包回归后，全套 **341 项主机测试通过（50.550 秒）**。协作分块截图的四帧复测通过：复制期间相邻输入服务最大间隔 **1.168ms**，独立 BLE 测试窗口最大输入采样间隔 **16.253ms**。详细证据、每帧复制总耗时与测量范围见 [开发说明](development.md)。尚未实测或确认的项目包括：琥珀／红／绿等其他灯色映射、具体 DOM 焦点或控件身份、其他未覆盖映射、物理断电与电池续航、电脑 Bluetooth 开关／长期休眠，以及持键跨断电。受控执行验证不改变界面上 submitted 与 Target not verified 的通用含义。
